# OCR ladder

Tesseract 5.5.3 / leptonica 1.87.0. The same purchase order at three scan qualities,
generated by `scripts/build_corpus.py` (seed 20260918) and measured through the real
ingest path: degrade → image-only PDF → `parse()` → OCR at 300 DPI.

| level | source DPI | blur | noise | JPEG | rotate | mean conf | status | fields |
|---|---|---|---|---|---|---|---|---|
| L1 clean | 300 | 0.0 | 0 | 95 | 0.0 | **95.1** | ingested | 5/5, unflagged |
| L2 medium | 200 | 1.0 | 4 | 35 | 0.6 | **62.4** | ingested | 5/5, all flagged low-confidence |
| L3 degraded | 150 | 1.2 | 5 | 30 | 0.7 | **43.4** | needs_review | extraction skipped |

## Thresholds

- **`MIN_OCR_CONFIDENCE = 55.0`** — between L2 and L3. Below it, human review instead
  of extraction. The demo PO sits at 95.1, well clear.
- **`LOW_CONFIDENCE_FIELD = 75.0`** — between L1 and L2. Between the two, values are
  extracted but every field is flagged rather than asserted flatly.

## Two measurement mistakes worth recording

**Measure the path the system actually takes.** An earlier pass rasterised the *source*
PDF at the target DPI and ran Tesseract on that, reporting 76.9 for L2. The pipeline
re-renders the already-degraded image-only PDF back up to 300 DPI, and that upscaling
adds interpolation damage the probe never saw. The true figure was 41.3 — a 35-point
error, enough to put the threshold in the wrong place.

**A cliff is not a gradient.** The first parameter set gave 95.1 → 44.4 → 0.0, with
Tesseract returning no words at all at the bottom. That makes the interesting middle
state — readable enough to extract, poor enough to distrust — untestable.

## Confidence and correctness

On this corpus the relationship was monotonic: values only corrupted once confidence
had already fallen below the review gate, so the gate caught what it was for. No
silent-corruption example was manufactured to fill the gap — a synthetic one would only
prove that a degradation script can be tuned until a threshold is crossed.

**This does not generalise, and a real document showed why.**
`eval/holdouts/gkdb0226.pdf` reads at **90.1** — above both thresholds, no flag, no
escalation — with two required fields lost entirely and the vendor name wrong
("Marista" for a letterhead reading "Arista"). Confidence scores the words Tesseract
found and is silent about the ones it dropped. That is what motivates escalating on a
field deficit as well as on low confidence (`eval/holdout_findings.md` §2).

The thresholds on this page are calibrated against a corpus that does not contain that
failure mode.

## Still missing: confidently wrong OCR

A high-confidence *wrong value*, as distinct from a high-confidence *missing* one.
Real sources, none present here:

- digit confusion in clean scans (`5`/`6`, `1`/`7`) — $12,480.00 read as $12,486.00
  with nothing to flag it
- dropped or misplaced thousands separators
- stamps and handwriting overlaying printed text, read confidently as the wrong layer
- table-adjacent values read correctly but bound to the wrong label
- toner streaks that remove a character cleanly rather than blurring it

How to build it: hand-author a scan whose ground truth differs from its OCR output in
a single digit, with measured high confidence on that token, and score it as its own
case. The point is not to pass — a system that cannot catch this should report that it
cannot.
